同一套脚本（`scripts/k6/full-api-load.js`、`scripts/k6/ai-rag-staged-load.js`、`scripts/performance/run-load-tests.ps1`）依次打 Spring 单体、Spring Cloud 网关、Go、Quarkus。本轮在压测过程中修复了 Cloud 读链路误拒流、Cloud 服务间依赖失败被放大成 500、Go 健康检查与动作接口缺失、RAG 别名首次创建失败等问题；下表数字均为**修复后**的最终一轮。

## 结论摘要

- **k6 全 API：四后端全部通过阈值。** `http_req_failed=0.000`，`checks=1.000`，健康检查、登录、驾驶员读、管理员读、超管读全部 1.000。

- **全 API 延迟排序：Go < Quarkus < Spring ≈ Cloud。** p95 分别为 2.4ms、8.9ms、49.6ms、51.3ms。Go 的优势主要来自更短的请求路径和更轻的 ORM/查询；Cloud 的 p99（176.5ms）明显高于 Spring（103.0ms），符合网关 + 多服务转发的尾延迟特征。

- **Cloud 误拒流已修复并复测。** 修复前空闲栈上 24 并发的端点探针中，`/api/roles` 206/240、`/api/permissions` 139/240、`/api/users` 101/240、`/api/vehicles` 113/240 返回 503，`/api/auth/me` 207/240 被放大成 `DEPENDENCY_TIMEOUT`；修复后 16c 管理端 6 路径探针 25,672 个请求全 200，driver 32c 仅 1.07% 503，48c 在连接池排队达到阈值时按设计拒流。
- **Cloud 修复前 AI/RAG 分段 RAG p95 为 34.4s，修复后为 42.7ms。** 同一脚本、同一台机；修复前 user 服务被误拒流，RAG 的 ACL 查询排队/超时。该对比只能说明故障已消除，不能当作精确的性能提升倍数。

## 口径

### k6 全 API

- 5 个场景：健康检查 2 VUs/20s；驾驶员读、管理员读各 8/6 VUs、40s；超管读 2 VUs/20s；登录 1 iter/s、20s。
- 阈值：`http_req_failed<0.02`、`p(95)<1500ms`、`p(99)<5000ms`、`checks>0.98`，各读链路 `>0.98`，健康/登录 `>0.99`。
- `http_reqs` 是 k6 实际发出的请求数；`rate` 是整轮平均 req/s，包含 setup 与各场景的 ramp 时间，不等于峰值。

### k6 AI/RAG 分段

- 到达率：AI actions 1/s、RAG 检索 1/s、RAG 管理 1/s、帮办循环 1/s、模型生成 1/s（仅 `-IncludeModel`）。
- `PERF_STRICT=true`，时长 20s；Go/Quarkus 开启 `-IncludeModel`，Spring/Cloud 未开启。
- 指标定义：
  - `ai_model_ok`：SSE 请求返回 200 且收到终止事件，**不保证真实模型调用**。
  - `ai_model_ollama_ok`：SSE payload 中带 `provider=ollama`。Go/Quarkus 的 SSE 事件没有 `provider` 字段，该指标按 0 记录，属于**结构性 N/A**，不能据此判定未调用 Ollama。
  - `ai_model_shed`：命中 `bulkhead_full` 或「模型繁忙」等准入控制标记。它是模型并发保护，不是 HTTP 失败。
  - `agent_draft_shed`：帮办草稿请求命中同一类降级标记。
  - `ai_model_noop_fallback_ok`：显式 noop fallback 比例；Go/Quarkus 本轮为 0。

### wrk

- 默认并发：driver 32c、admin 48c、super 32c、RAG 8c、RAG 管理 8c、AI actions 8c、login 16c，每场景 20s，4 threads。
- 另做同并发基线 16/16/8/8（Go、Quarkus），用于比较“不触发拒流时”的读吞吐。
- **只使用 wrk 的 `Requests/sec` 与 `Non-2xx` 计数**。本轮多组 `Requests/sec × 平均延迟 > 连接数`，物理上不可能（如 Cloud admin 1,246.46 × 96.25ms ≈ 120 在飞 > 48 连接；Go login 27,176 × 22.77ms ≈ 619 > 16）。wrk 跑在 Docker 内、宿主同时承载所有服务，高 RPS 下回调时间戳包含调度延迟，导致平均延迟被高估。延迟结论以 k6 为准，wrk 延迟不进入横向结论。
- wrk 的 `read-mix.lua` 按线程维护 `current_path`，一个线程驱动多条连接时端点归属会错位。**端点级非 2xx 表不作为证据**；需要端点级结论时使用单路径探针（`scripts/wrk/status-probe.lua`）。
- 「2xx 吞吐」= `Requests/sec × (1 - Non-2xx/总请求)`，由两个直接计数推导，不含登录场景。

- Cloud 的 `ai_http_orchestration_ms` 是所有后端里唯一越过严格阈值的指标，k6 进程以 99 退出并打印 `thresholds on metrics 'ai_http_orchestration_ms' have been crossed`。同一轮 `ai_action_ok`、`agent_loop_ok`、`agent_draft_ok`、RAG 与 checks 均为 1.000，`http_req_failed=0`，另有 6 个 `dropped_iterations`。这不是 HTTP 失败，而是模型路径延迟。

## 负载拒流横向对比

| 后端 | 过滤器 | 非台账 GET 触发 | 台账写触发 | 健康检查 | 响应 |
| --- | --- | --- | --- | --- | --- |
| Spring | `ReliabilityGuardFilter`（`@Order(-90)`） | servlet 在飞 > Hikari 最大池，或利用率 ≥0.8 | 有等待连接，或利用率 ≥0.8 且无空闲连接 | 豁免 | 503 `LOAD_SHED` + `Retry-After: 1` |
| Cloud | `PoolLoadShedFilter` | 等待连接 ≥ max(1, 最大池/2) | 有等待连接，或利用率 ≥0.8 且无空闲连接 | 豁免 | 503 `LOAD_SHED` + `Retry-After: 1` |
| Go | `reliability.ShedRequest` | 利用率 ≥0.8 | 有等待连接，或利用率 ≥0.8 且无空闲连接 | 豁免 | 503 `LOAD_SHED` |
| Quarkus | `LoadShedFilter` | 在飞 > 最大池（20），或利用率 ≥0.8 | 有等待连接，或利用率 ≥0.8 且无空闲连接 | 豁免 | 503 `LOAD_SHED` + `Retry-After: 1` |

观察到的差异：

- **Spring super mix 63.10%**：Hikari 最大池 32，wrk 32c，池利用率很容易到 100%；策略会对所有非台账 GET 一起拒流，即使该请求本身不查库。这是“保护连接池”的直接代价，粒度偏粗。
- **Cloud admin mix 22.20%**：池 16、队列阈值 8，48c 已超出容量；16c 为 0。修复解决的是“中等并发误拒”，不是“无限并发不拒”。
- **Quarkus driver 28.58% / admin 11.14%**：非台账 GET 按利用率拒流，driver mix 的单请求 DB 工作更重，先饱和；16c 下两端均 0。
- **Go 默认并发 0 非 2xx**：查询路径更轻，48c 仍未把池利用率推到 0.8；容量上限未探到。
- 503 是保护动作，不应与登录 429、鉴权 401/403 混为一类。所有探针的 503 body 均为 `LOAD_SHED`；Cloud 修复前的 `DEPENDENCY_TIMEOUT` 已不再出现。

| Go | 0.571 | 1.000 | 3.6ms | 2.4ms |

方向性变化：

- Go 从 0.571 提升到 1.000，主要是补上了 readiness 与 actions 两个契约缺口；这不是单纯的性能提升。
- Quarkus p95 从 101ms 降到 8.9ms，与前置的 SSE/拒流计数修复及本轮启动配置有关，不能全部归因于代码版本。
- Cloud p95 从 97ms 降到 51.3ms，但 p99 仍有 176.5ms；网关链路尾延迟依旧高于单体。
- 两轮的主机负载、数据量、Ollama 状态和脚本场景并不完全一致，**该表只用于看方向，不作为严格回归结论**。

## 遗留问题与建议

1. **Cloud AI 编排 p95 超阈值**（4,970ms > 1,200ms）。`ChatAgent.chatWithActions` 与帮办草稿都同步调用模型；在 1+1 req/s、Ollama 并行度 2 的条件下排队明显。建议二选一：把 actions 改为规则优先、模型兜底（与 Spring/Go/Quarkus 对齐），或为该模型型端点单独定义 SLO，不要继续套用 1.2s 的规则编排阈值。本轮未改，因为这会改变 Cloud 的 AI 编排语义，属于产品决策而非压测缺陷。
2. **Cloud 帮办循环 p95 5,911ms、dropped_iterations=6**。与上一条同源；如果前端依赖该接口的交互时延，应把草稿生成移出同步路径或增加明确的排队上限。
3. **Spring super mix 在 32c 下 63.10% 拒流**。策略对“不查库的 GET”也会因池利用率拒流。若 super 读链路需要在该并发下保持可用，可参考 Cloud 的队列深度策略，或把非 DB 端点从该过滤器的影响面中拆出。
4. **wrk 延迟不可用于横向结论**。本轮多组 `rps × 平均延迟 > 连接数`；需要延迟对比时以 k6 为准。若要继续用 wrk 做延迟，应把 wrk 放在独立主机或限制 RPS，避免回调调度延迟污染时间戳。
5. **登录 429 是预期限流**。登录 wrk 场景的 99.9%+ 非 2xx 不应作为可用性失败；真实登录成功率应看 k6 `login_ok`（本轮四端均 1.000）。
6. **Ollama NUM_PARALLEL=2 是当前模型链路的硬约束**。Go 的 `ai_model_shed=0.476` 与 Cloud 的 5s 级 p95 都指向同一瓶颈；提高并行度前应先确认显存/内存与模型服务的稳定性。
