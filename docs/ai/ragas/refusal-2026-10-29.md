# RAG 拒答能力改造报告（2026-10-29）

> **引用合规口径（2026-10-30 重述）**：本报告的「引用合规」分母已改为**已交付答案**（剔除
> provider 错误与护栏拒答），括号内保留旧口径（含拒答，等价于 1 − 拒答率）。变更原因见
> [baseline-2026-10-30-topk10.md](baseline-2026-10-30-topk10.md) 的「指标口径提醒」；
> 原始产物 `artifacts/` 未回溯改写。

本报告记录 Spring 主后端纯 RAG 模式下的拒答（abstention）能力改造。此前五组 RAGAS 运行的
不可回答问题真实拒答率都是 0/3：检索 topK 总能返回若干段落，引用护栏又只校验“编号存在且
在范围内”，模型因此会把相邻业务的资料拼成答案。本轮在引用护栏之后增加一次生成后主题校验，
把“资料讲的不是这个问题所问的业务”变成拒答；随后把同一实现移植到 Cloud。

## 结论摘要

- 不可回答拒答从 0/3 提升到 **3/3（100%）**。三次拒答都由生成后校验触发，答案模型自身仍然
  没有主动弃答；本报告不把护栏拒答算作模型能力。
- 本轮 27/30 可评分（90.00%）。被排除的 3 条是 a10（引用修复后仍无引用，引用护栏拒答）、
  a16 与 a28（主题校验误拒）。
- 可评分样本上 Faithfulness 0.9907、Response Relevancy 0.8521、Context Precision 0.9949（26 条）、
  Context Recall 0.9815、Answer Correctness 0.7713；引用合规 1.0000（27/27，旧口径 0.9000），
  fallback、上下文漂移、provider 错误、ACL 泄漏均为 0，无硬失败。
- 与 `improvement4-20261028` 的 27 条共有样本配对比较：Faithfulness +0.0031、Response
  Relevancy −0.0404、Context Precision 0.0000、Context Recall 0.0000、Answer Correctness
  −0.0134，均在 llama3.2 与裁判的波动范围内；检索代码未改动。
- 代价是可回答题的误拒：本轮 2/29 条合格答案被误拒（6.9%），a16 的检索首条就是该题的直接依据，
  a28 的两段资料分别覆盖两个子问题。24 条 dev 校准样本没有暴露这类边界误判，说明小样本校准
  不足以保证泛化。
- 特性是显式开启的：未配置 `AI_GUARDRAIL_TOPIC_MODEL` 时校验关闭并打印 WARN，默认部署的拒答
  行为不变。本轮评测显式配置 `qwen2.5:7b`，并把超时从默认 `PT12S` 放宽到 `PT20S`。
- Cloud 已移植同一实现，AI 模块 72 个测试通过；Cloud 侧尚未用本特性复跑 RAGAS。

## 缺口与方法

### 1. 拒答缺口在哪里

`AnswerGroundingPolicy` 只能确认回答里存在合法引用编号；它不检查编号指向的段落是否在讲用户
所问的业务。`improvement4-20261028` 的 u01 就是例子：问题问车辆报废，检索回来的是过户、超速、
申诉等段落，模型复用“车辆过户”的上下文补出了不受支持的办理步骤，引用编号却全部合法。

只在检索侧加阈值也解决不了：topK 近似必然返回结果，BM25 分数又随语料变化，没有稳定的“无相关
内容”判据；是否该拒答取决于“问题与资料的主题关系”，这是答案层的判断。

### 2. 生成后主题校验

新增 `TopicGroundingVerifier`：答案通过引用护栏后，用一个独立裁判模型同时看问题、检索资料和
草稿回答，只判断主题是否对得上，不评价答案是否完整或正确。判定 false 时用
`NO_SOURCE_ANSWER` 替换整段回答；判定 true、超时、模型不可用或输出无法解析时放行（fail-open）。

选择主题判断而不是蕴含判断，是因为校准表明更强的判据在当前裁判上不可用：

- `topic_only`（只看问题与回答）看不到资料，资料缺失但回答仍在主题上时会漏放；
- `evidence_gate`（只看资料是否覆盖问题）在 dev 集上把 6/11 条可回答答案判成不覆盖，无法上线。

因此当前版本只承诺“资料覆盖所问主题、回答不换题”，不承诺“资料支持结论”。后者仍是已知缺口。

### 3. 提示词校准

校准集与 RAGAS 评测集主题不重叠：12 道可回答题 + 12 道不可回答题。可回答题中的 e08 手工标注
为应拒答（该答案先声明无法回答，随后把问题换成了车辆注册），因此放行分母是 11，应拒答分母
是 13。四种候选提示词各跑一遍 `qwen2.5:7b`，`temperature=0`、`num_predict=64`、`seed=42`、
JSON schema：

| 提示词 | 可回答放行 | 应拒答拦截 | 结论 |
| --- | ---: | ---: | --- |
| `source_topic`（带示例） | 10/11 | 13/13 | 一条误拒 |
| `source_topic_no_example`（当前实现） | 11/11 | 13/13 | 选中 |
| `topic_only`（不看资料） | 10/11 | 10/13 | 漏放 3 条 |
| `evidence_gate`（不看回答） | 5/11 | 13/13 | 误拒过多 |

示例会让裁判把示例措辞当成判据，去掉示例后 dev 集上完全分开。这个结果只说明提示词在 24 条
dev 样本上的行为，不是泛化保证。

## 实现

### 1. `TopicGroundingVerifier`

- 输入：问题、清洗后的答案、`RetrievalResult` 列表。资料按 `[n] 正文` 拼接，复用产品上下文的
  编号方式。
- 输出：JSON `{"topic_in_sources": boolean, "reason": string}`；解析支持严格 JSON、首个 `{` 到
  最后一个 `}` 的切片，以及字符串形式的 `"true"`/`"false"`。
- 跳过：校验关闭、问题或答案为空、资料为空、答案已经是两种标准拒答文本、资料中含
  `WEB_SEARCH` 来源、所有资料正文为空。网页片段是实时搜索结果，不在校准范围内。
- 裁判调用走 `AiProviderRegistry.completeIsolated`：不触发 fallback，也不计入聊天 provider 的
  失败计数。裁判模型故障不能打开服务聊天流量的熔断器。

### 2. Provider 的单次调用能力

`AiGenerationOptions` 增加 `model` 与 `responseFormat`，并提供
`forVerification(timeout, model, responseFormat)`：`temperature=0.0`、`maxTokens=96`、重试 0 次。
Ollama 在请求体中发送 `options.temperature`、`options.num_predict` 和 `format`（JSON schema）；
OpenAI 兼容 provider 发送 `response_format: {"type":"json_object"}`。这样校验调用不依赖全局
聊天模型配置。

### 3. 流水线位置

`ChatPipeline` 在纯 RAG 回合缓冲完文本事件后依次执行：

1. 清洗内部标签；清洗后为空则进入引用修复或拒答；
2. 引用护栏；无引用先做一次引用修复重试，仍无引用则拒答；
3. 主题校验；false 时用 `NO_SOURCE_ANSWER` 替换整段回答，true 时回放清洗后的文本。

`QUEUE` 与 keep-alive 仍然即时透传且不进入判定；`TOOL`/`DRAFT`/`RESULT`/`ACTION`、ERROR 与
`isFallback` 事件继续原样透传。拒答替换沿用第一次请求的 `messageId`，一个 SSE 流不会出现两个
消息身份。Agent 路径不接入该校验，因为没有可判定的检索资料列表。

### 4. 配置

```yaml
ai:
  guardrail:
    topic-verification:
      enabled: ${AI_GUARDRAIL_TOPIC_VERIFICATION:true}
      model: ${AI_GUARDRAIL_TOPIC_MODEL:}
      timeout: ${AI_GUARDRAIL_TOPIC_TIMEOUT:PT12S}
```

`enabled=true` 且 `model` 非空时才真正启用；`model` 为空时启动日志打印 WARN 并保持关闭。这样
避免默认部署把生成答案的聊天模型拉来做自审。

### 5. Cloud 移植

`finalassignmentcloud-ai` 增加同逻辑的 `TopicGroundingVerifier`、相同的 `ChatPipeline` 接线、
provider 单次调用能力与隔离调用、相同的配置项和 7 个校验器测试；另新增 provider 层测试，验证
per-call 模型与 JSON schema，以及“隔离调用失败 3 次后聊天流仍走主 provider”。

## 局限

- **主题校验不等于蕴含校验**：资料覆盖了所问业务、但缺少具体事实时仍会放行；回答在正确主题下
  编造细节也不会被这一层拦住。`evidence_gate` 提示词的校准失败说明当前裁判做不了更强的判断。
- **误拒是真实成本**：本轮 2/29 条合格答案被误拒，其中 a16 的判据几乎逐字出现在资料里。提高
  裁判能力（更大模型、两次判定、逐子问题拆分）比继续改提示词更有希望降低误拒。
- **只跑了一轮 30 题**：单一裁判、单一答案模型，均值和误拒率的置信度有限；不能用 0.01 级别的
  指标差解释为确定收益。
- **默认关闭**：不配置 `AI_GUARDRAIL_TOPIC_MODEL` 时行为与改造前一致，默认部署的不可回答拒答
  仍是 0/3。本轮把超时放宽到 `PT20S`，默认 `PT12S` 下裁判超时会直接放行。
- **Cloud 未复跑 RAGAS**：Cloud 侧只有单元测试与编译验证；部署时必须同样配置裁判模型与可达的
  Ollama 地址，否则校验保持关闭（启动日志会打印 WARN）。
- **只覆盖纯 RAG 模式**：Agent 模式仍走工具路由，不适用本报告结论。

## 结论与后续

- 采纳：生成后主题校验作为显式开启的能力，与引用护栏串联；引用护栏的语义不变，没有引用仍然
  不回答。
- 下一步优先级：把误拒从 6.9% 降下来，再谈更强的拒答。可行方向是换更强裁判、对多跳问题按
  子问题分别判定，以及在主题校验失败时先做一次“按资料重写”再判定，而不是直接拒答。
- 需要单独立项的是蕴含判断：确认引用段落真的支持结论，而不是只确认主题相同。
- 已记录的工程边界不变：DEPARTMENT ACL 身份折叠、ES alias 自动创建、扫描版 PDF/OCR。
