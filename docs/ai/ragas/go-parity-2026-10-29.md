# Go 后端拒答能力移植报告（2026-10-29）

本报告记录把 Spring 主后端的答案层拒答能力移植到 `final_assignment_backend_go` 的过程与边界。
Spring 的改造与评测结论见 [refusal-2026-10-29.md](refusal-2026-10-29.md)；Cloud 的移植见
[cloud-parity-2026-10-28.md](cloud-parity-2026-10-28.md)。

## 结论摘要

- Go 现在与 Spring 同构：**清洗内部标签 → 引用护栏（无引用先做一次引用修复）→ 生成后主题校验
  （fail-open）**，拒答文本与 Spring 逐字一致。
- 修复了一个会污染全部护栏判断的缺陷：provider 在流结束时把整段回答重复作为一个终止 token
  发出。此前任何引用判定都会看到两遍答案，SSE 客户端也会收到重复正文。
- 纯 RAG 回合按 `messageId` 聚合，一次 SSE 流只有一个消息身份；引用修复沿用首个 `messageId`。
- 新增 `AI_AGENT_ENABLED` 纯 RAG 开关；默认仍路由 Agent（与此前行为一致），评测时需要显式关闭。
- 引用护栏默认开启：**检索被请求（或默认）启用但结果为空/检索失败时，聊天会拒答**
  （`NO_SOURCE_ANSWER`）。这是相对旧行为的默认变更，可用
  `AI_GUARDRAIL_CITATION_ENFORCEMENT=false` 回退到旧行为。
- 本轮没有对 Go 后端执行 RAGAS：本地 ES 栈未启动，Go 的 embedding 也仍指向非 Ollama 配置。
  该评测按计划单独排期，见文末复现步骤。

## 移植范围

| 能力 | Spring | Go 移植 |
| --- | --- | --- |
| 内部标签清洗 | `AnswerTextSanitizer` | `internal/ai/guardrail/sanitizer.go` |
| 引用护栏与标准拒答文本 | `AnswerGroundingPolicy` | `internal/ai/guardrail/policy.go` |
| 一次引用修复重试 | `ChatPipeline` | `guardrail.Stage` + `PromptAssembler.AssembleCitationRepair` |
| 生成后主题校验 | `TopicGroundingVerifier` | `internal/ai/guardrail/verifier.go` |
| 按次模型 / JSON 输出 / 独立超时 | `AiGenerationOptions` + provider 隔离调用 | `GenerationOptions` + `IsolatedCompleter` + `OpenAIProvider.Complete` |
| 提示词只暴露 `[n]` 与正文 | `ContextBuilder` | `ContextBuilder.BuildWithSources` |
| 单 `messageId` | `ChatPipeline` | `ChatPipeline.Stream` |
| 纯 RAG 模式 | `AI_AGENT_ENABLED` | 同名环境变量 |

明确未移植：多 provider 抽象、熔断与 fallback。Go 的 provider 层本来就没有这些机制，裁判调用
只是走独立的 HTTP client，不会影响聊天流量的可用性。

## 实现

### 1. 终止 token 修复

`OpenAIProvider.parseSSEStream` 原先在收到 `[DONE]` 或带 `finish_reason` 的分片时，把
`fullText.String()` 作为终止 token 再发一次。流式分片已经把正文逐段发出，终止 token 只是一个
哨兵值。现在终止 token 只携带 `Finished: true`，`streamFromProvider` 也跳过空文本 token：

```go
// Check for stream end. The terminal token is a sentinel only: the answer text was
// already streamed chunk by chunk, so repeating it here would duplicate the reply.
if data == "[DONE]" {
    tokenChan <- service.AiToken{Finished: true}
    return nil
}
```

修复后 `Stream` 的全部 token 拼接结果与模型输出逐字相等，测试用 `strings.Join` 断言这一点。

### 2. 清洗与引用护栏

- `Sanitize` 移植 `AnswerTextSanitizer`：剥离 `retrieved_context` / `conversation_window` 等内部
  标签、占位引用 `[n]`、句子开头的连接词，并规范空格与标点。
- `CitationPolicy.Evaluate` 与 Java 版逐条对应：半角 `[1]`、全角 `【1】`、分组 `[1,2]` /
  `[1，2]`，编号必须落在实际进入提示词的资料范围内；也接受答案中出现显著的来源标识、文档
  ID 或标题（中文 ≥2 字，拉丁字母 ≥4 字符且含字母，避免 `12` 这类裸编号误判）。
- 无引用时先做一次引用修复（仅纯 RAG 路径；Agent 路径不复用工具调用），仍无引用用
  `UNCITED_ANSWER` 拒答；完全没有可用资料时用 `NO_SOURCE_ANSWER` 拒答。两条文本与
  `AnswerGroundingPolicy.java:23-26` 逐字一致，`scripts/ragas/ragas_eval/sse.py` 按字节比较。

### 3. 单次调用与隔离裁判

- `service.GenerationOptions` 描述一次非流式调用：`Model`、`Temperature`、`MaxTokens`、
  `ResponseFormat`、`Timeout`、`RetryAttempts`。
- `VerificationOptions` 固定裁判画像：`temperature=0`、`maxTokens=96`、不重试。
- `OpenAIProvider.Complete` 使用独立的 `completionClient`（仅 5s 拨号超时，整体受 `ctx` 约束）。
  聊天流仍使用 700ms 响应头超时的 client，两者互不影响——7B 裁判不可能在 700ms 内返回。
- 裁判请求发送 `response_format: {"type": "json_object"}`。本地 Ollama（`/v1/chat/completions`）
  实测接受该字段并返回合法 JSON；不支持的网关会返回 4xx，此时裁判失败并按 fail-open 放行。

### 4. 主题校验

`Verifier` 的提示词、跳过条件与幂等语义照搬 `TopicGroundingVerifier`：

- 输入：原始问题、清洗后的答案、实际进入提示词的资料；资料按 `[n] 正文` 拼接。
- 输出：`{"topic_in_sources": boolean, "reason": string}`；解析支持严格 JSON、首尾花括号切片、
  字符串形式的 `"true"`/`"false"`。
- 判定 false 时用 `NO_SOURCE_ANSWER` 拒答；判定 true、超时、请求失败或解析失败一律放行。
- 跳过：校验关闭、问题或答案为空、资料为空、答案已是标准拒答文本、资料中含 `WEB_SEARCH`
  来源、所有资料正文为空。Go 目前不把网页结果并入 RAG 资料列表，这一条是为与 Spring 保持
  一致的防御性规则。
- `AI_GUARDRAIL_TOPIC_MODEL` 为空时校验保持关闭并在启动日志打印 WARN，避免把聊天模型拉来自审。

### 5. 流水线接线

`ChatPipeline.Stream` 的顺序：

1. 判断 `ragEnabled`；检索后调用 `AssembleWithSources`，拿到实际进入提示词的资料前缀。
2. 生成 `messageId`，Agent 前缀事件、provider token/done/error 都打上同一身份。
3. 纯 RAG 回合交给 `guardrail.Stage.Wrap`：缓冲 token，结束后清洗 → 引用判定 → 一次修复 →
   主题校验；通过则回放原 token（清洗有变化时改为一个清洗后的 token），拒答则输出单个标准
   文本 token，两种情况下都只发一个 `done`。
4. 出现 `TOOL`/`DRAFT`/`RESULT`/`ACTION` 等控制事件时，立即冲刷已缓冲 token 并转为逐 token
   透传，不再判定——拒答不能吞掉工具卡片或导航动作。`error` 立即透传并丢弃缓冲。
5. `ragEnabled=false` 的请求级关闭不进入护栏；Agent 路径仍受护栏约束（与 Spring 相同），但
   不提供引用修复。

上下文预算只决定“模型看到了哪几段”，护栏判断的也是同一子集；被截断掉的资料不能作为回答
依据通过检查。

## 配置

Go 全部读取环境变量，与 Spring/Cloud 同名：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `AI_AGENT_ENABLED` | `true` | `false` = 纯 RAG，不路由工具 |
| `AI_GUARDRAIL_CITATION_ENFORCEMENT` | `true` | 无引用不回答；关闭后仍做标签清洗 |
| `AI_GUARDRAIL_TOPIC_VERIFICATION` | `true` | 需同时配置裁判模型才生效 |
| `AI_GUARDRAIL_TOPIC_MODEL` | 空 | 空 = 关闭并打印 WARN |
| `AI_GUARDRAIL_TOPIC_TIMEOUT` | `12s` | 裁判调用超时；评测建议 `20s` |

聊天请求的总预算从 2 分钟放宽到 3 分钟，覆盖生成、一次引用修复和一次裁判调用。

## 未完成：Go RAGAS

本轮没有对 Go 执行 RAGAS，原因是评测前置条件未满足：

- 本地 Elasticsearch（9400）与 Docker Desktop 未启动，`/api/rag/query` 无法返回检索结果。
- `gozero-api.yaml` 的 embedding 仍不是 Ollama `nomic-embed-text`，需要先切换配置并重建
  `rag_chunk_go_v1` 索引，否则 `seed.py` 在 ES alias 可见性检查处必然失败。

代码侧的前置条件已经具备：Go 有登录、`/api/rag/query`、管理端 seed 与 embedding 端点，
并会真实写入 ES。复现步骤：

```bash
cd final_assignment_backend_go
PORT=8080 AI_AGENT_ENABLED=false RAG_RETRIEVAL_ENABLED=true \
AI_GUARDRAIL_TOPIC_MODEL=qwen2.5:7b AI_GUARDRAIL_TOPIC_TIMEOUT=20s \
go run ./project/cmd/app
```

```bash
cd scripts/ragas
RAGAS_BASE_URL=http://127.0.0.1:8080 RAGAS_ES_URL=http://127.0.0.1:9400 \
RAGAS_INDEX_ALIAS=rag_chunk_go_current RAGAS_TARGET_LABEL="Go 后端（拒答校验）" \
uv run ragas-eval run --top-k 5 --run-id 20261029-go-refusal
```

在该评测完成前，Go 的拒答效果只有单元测试与手工 SSE 验证，不宣称 RAGAS 指标。

## 风险与边界

- **默认行为变更**：引用护栏默认开启。ES 不可用或检索为空时，聊天会返回 `NO_SOURCE_ANSWER`；
  依赖“无资料自由问答”的部署需要显式设置 `AI_GUARDRAIL_CITATION_ENFORCEMENT=false`。
- **误拒**：主题校验的误拒在 Spring 实测为 2/29；Go 的检索质量与 Spring 不同，误拒率未测。
- **延迟**：纯 RAG 回合需要先缓冲完整回答再多一次裁判调用（Spring 同链路约 +276ms 量级）。
- **主题校验不等于蕴含校验**：资料覆盖主题但缺少具体事实时仍会放行，回答在正确主题下编造
  细节不会被这一层拦住。
- **Agent 路径**：有控制事件时不做判定；无控制事件的 Agent 回答与 Spring 一样受引用护栏约束，
  但没有引用修复重试。
