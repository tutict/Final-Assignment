# Go 后端 RAGAS 评测报告（2026-10-29）

本报告记录 `final_assignment_backend_go` 的 RAGAS 端到端评测：暴露的三处对齐缺口、修复、
评测配置、结果与基线对比。答案层拒答能力的移植见 [go-parity-2026-10-29.md](go-parity-2026-10-29.md)；
Spring 参考实现的改造与基线见 [refusal-2026-10-29.md](refusal-2026-10-29.md)；Quarkus 后端的
同类评测见 [quarkus-rag-elasticsearch-2026-10-29.md](quarkus-rag-elasticsearch-2026-10-29.md)。

## 结论摘要

- Go 后端**第一次跑通完整 RAGAS 链路**：不可答拒答 **3/3**、ACL 泄漏 **0**、上下文漂移 **0**、
  provider 错误 **0**、硬失败 **0**，五项 RAGAS 均值全部达标。
- 与 Spring 基线**同数据集、同裁判、同模型、同 topK**（四个 hash 与模型指纹逐一相同，见
  「可比性」），检索侧指标 Context Precision / Context Recall 分别为 **1.0000 / 1.0000**，
  高于基线的 0.9949 / 0.9815。
- 首轮评测暴露三处**互相叠加**的缺陷，导致不可答问题完全不被拒答（0/3）。三处都修掉后拒答率
  回到 3/3，Faithfulness 由 0.9345 升到 0.9667，Context Precision 由 0.9643 升到 1.0000。
- Go 的检索层是**确定性**的：与 Spring 基线相比 33/36 题 top-5 集合相同、29/36 题顺序相同；
  与自己的上一轮运行相比 36/36 题集合与顺序**完全一致**。
- 可回答题的误拒为 3/30（10%），与 Spring 的 3/30 持平；被拒的三题不同（见「误拒分析」）。
- **遗留缺陷（跨后端，非本次移植引入）**：服务端把部门身份折叠成字面量 `DEPARTMENT` /
  `ALL`，而语料里存的是真实部门名（`finance` / `traffic-police`），因此 `DEPARTMENT` 作用域的
  文档对任何调用方都不可见。详见「已知限制」。

## 首轮暴露的缺陷与根因

首轮运行（`20261029-go-weights-topic`，commit `e70613dc`）五项均值全部达标，但**不可答拒答
0/3**：`u01`/`u02`/`u03` 全部被正常回答成编造内容。逐层排查后定位到三处独立缺陷，缺一不可。

### 1. 对话链路丢弃调用方下发的 topK

评测脚本给 `/api/ai/chat/stream` 传 `metadata={"ragTopK": 5}`。`buildRagRequest` 原先只断言
`metadata["topK"].(int)`，而 JSON 数字解码后是 `float64`，断言直接失败，请求静默退回默认的
10 条——聊天链路拿到的上下文比评测要求的宽一倍。`ragTopK` 分支甚至排在 `topK` 之后，与 Spring
的 `intValue(metadata, "ragTopK", "topK")` 优先级相反。

修复：新增 `metadataInt` 兼容 `int`/`int32`/`int64`/`float32`/`float64`/`json.Number`，并按 Spring
的顺序让 `ragTopK` 优先于 `topK`（`project/internal/ai/chat_pipeline.go:261`）。

### 2. 裁判请求下发完整 JSON Schema

`OpenAIProvider.Complete` 把 `options.ResponseFormat` 原样塞进 `response_format`。Spring 的原生
provider 下发的是 JSON Schema（结构化输出），而 OpenAI 兼容 provider 降级为
`{"type": "json_object"}`——`OpenAiCompatibleProvider.java:217-221` 有明确注释说明兼容端点的
JSON Schema 支持参差不齐。Go 走的是兼容端点，却下发了 Schema，Ollama 直接忽略，裁判于是用散文
包裹 JSON 回答。

修复：`response_format` 统一降级为 `{"type": "json_object"}`，提示词里保留所需键名
（`project/internal/provider/openai_provider.go:128`）。

### 3. 判定解析按首个 `{` 到末个 `}` 切片

`parseVerdict` 先尝试整体解析，失败后取 `strings.Index(raw, "{")` 到 `strings.LastIndex(raw, "}")`
之间的文本。裁判在散文里回答时，这个区间会跨过多个对象甚至截断在字符串中间，JSON 解析失败，
判定为 `nil` → **fail-open 放行**。这正是不可答问题不被拒答的直接原因。

修复：改为逐个平衡括号扫描（忽略字符串内的花括号），取最后一个带 `topic_in_sources` 的对象——
模型先起草结论再自我修正时，最终意见在最后（`project/internal/ai/guardrail/verifier.go:178`）。

三处修复后实测：同样的 `metadata={"ragTopK":5}` 请求下，`u01`/`u02`/`u03` 全部返回标准的
`NO_SOURCE_ANSWER` 拒答文案，后端日志出现且仅出现 3 条 `Topic verification refused an answer`；
对照题 `a16`/`a24` 正常作答，无误拒。

### 关于「与基线偏差 ≤ 0.03」这条验收带

检索侧指标（Context Precision / Context Recall）偏差为 **+0.0051 / +0.0185**，稳定落在带内。
生成侧指标（Faithfulness / Relevancy / Answer Correctness）的偏差分别是 −0.0241 / +0.0371 /
+0.0396，两项越界，但这条带**低于本数据集生成侧的噪声底**，不能作为回归判据：

- Go 首轮 → Go 本轮（同一检索结果，仅改答案生成与护栏），25~26 题配对差：Faithfulness 均值
  −0.0218（单题最大 −0.2500），Answer Correctness 均值 −0.0188（单题最大 −0.3917）。
- Spring 基线 → Go 本轮配对差：Faithfulness 均值 −0.0260（单题最大 −0.4000）。
- Context Precision / Context Recall 在 Go 首轮 → Go 本轮的配对差恒为 **0.0000**。

也就是说：检索侧可复现，生成侧随采样摆动，同一构建两次运行的生成侧配对差就能吃掉整条带。
这条结论与 Quarkus 后端一致（见
[quarkus-rag-elasticsearch-2026-10-29.md](quarkus-rag-elasticsearch-2026-10-29.md) 的同节）。

### 检索层对比

Go 本轮 vs Spring 基线：36 题中 **33 题 top-5 集合相同、29 题顺序相同**；7 题存在差异
（`a02` / `a11` / `a15` / `a19` / `a25` / `a28` / `u01`），差异形态是 top-5 内部的相邻换位或
末位替换，例如 `a02` 的 Spring 结果含 `c-license-points`，Go 结果含 `c-fine-payment-guide`。
两端的混合检索实现不同（Spring 走 ES 原生 BM25 + kNN，Go 走自研 RRF 融合 + 词法重排），
排序细节本就不会逐位一致。

Go 本轮 vs Go 首轮：36 题**集合与顺序全部一致**（36/36），证明 Go 自身的检索链路是确定性的，
两轮之间的指标差异只来自答案生成与护栏。

### 误拒分析

两端的可回答题误拒数相同（3/30 = 10%），但被拒的题不同：

| 后端 | 被拒的可回答题 | 拒答类型 |
| --- | --- | --- |
| Spring 基线 | `a10` 记分周期、`a16` 超速处罚、`a28` 年检过户 | `a10` 无引用，其余 `no_source` |
| Go 本轮 | `a24` 超期申诉、`a25` 微信支付宝缴纳、`a28` 年检过户 | 全部 `no_source` |

- `a24`：Go 与 Spring 检索结果**完全相同**（含 `c-appeal-deadline`），拒答差异来自裁判判定，
  属生成侧噪声。
- `a25`：Go 的 top-5 把 `c-fine-late-fee` 提到第 2 位，但第 1 位 `c-fine-payment-methods` 仍
  覆盖问题，拒答仍属误拒。
- `a28`（两端都拒）：Go 的 top-5 **丢掉了 `c-vehicle-transfer`**（过户），上下文里确实没有过户
  资料，此处的拒答在给定上下文下是合理的——这是检索侧的取样差异，不是护栏缺陷。

不可答三题在两端都是 3/3 拒答，没有出现「拒答能力只对特定题生效」的情况。

## 已知限制

- **DEPARTMENT 作用域文档对所有人不可见（跨后端既有缺陷）**。服务端把部门身份折叠成字面量
  `DEPARTMENT`（业务角色）或 `ALL`（系统角色），而语料里存的是真实部门名
  （`c-dept-finance-sop` → `finance`、`c-dept-traffic-sop` → `traffic-police`）。两者永不相等，
  于是 `DEPARTMENT` 作用域的 2 篇文档不会被任何身份检索到。该行为与 Spring 参考实现逐字一致
  （`RagQueryController.java:42-52` 推导部门、`AclFilterService` 按真实部门名匹配），本次移植
  保持一致而未单方面改动，因此 `p03` 探针虽然 PASS，但覆盖的是「ROLE / USER」两种作用域，
  DEPARTMENT 作用域实际处于「一律拒绝」状态。修法需要同时改服务端推导、语料元数据与各后端，
  属于独立议题。
- **生成侧指标不可复现**。见「关于『与基线偏差 ≤ 0.03』这条验收带」。单次运行不能用作回归判据。
- **主题校验只覆盖主题，不覆盖事实**。资料覆盖主题但缺少具体数字时仍会放行，编造细节不被这一
  层拦住。
- **默认拒答行为变更**。引用护栏默认开启，ES 不可用或检索为空时聊天返回 `NO_SOURCE_ANSWER`，
  需要「无资料自由问答」的部署必须显式设置 `AI_GUARDRAIL_CITATION_ENFORCEMENT=false`。
- **评测期间共用 `rag_embedding_task` 表**。Spring / Go / Quarkus 的嵌入 worker 若同时运行会
  抢走任务并写进各自的索引。本轮 Go 用的是自己已建好的 `rag_chunk_go_768_v1`，未触发嵌入流程。
