# ADR-001: Full Loop for Appeal Mutation Idempotency

## Status

Accepted by the Supervisor before implementation.

## Context

Observed local boundaries span Spring and Flutter, a durable request-history row,
an appeal insert, an authenticated identity, duplicate/concurrent delivery,
response parsing, retry lifecycle, and compatibility with existing appeal
workflow behavior. A partial success between history and appeal writes could make
a retry either duplicate an insert or incorrectly suppress work.

## Decision

Use Full Loop mode with one cohesive Loop, separate backend and frontend
implementation Tasks, an explicit integration Task, independent Spec and
Standards review, and specialist Data, Concurrency, Security, Compatibility, and
Frontend review.

Use the existing `sys_request_history` unique idempotency key as the durable
serialization boundary. No schema or migration change is permitted. The concrete
service design remains a TASK-002 implementation decision subject to review.

## Consequences

- Contract, Implementation, Integration, Review, and Closure barriers are
  mandatory.
- Findings require Supervisor triage, a scoped rework Task, and original Reviewer
  reverification.
- Delivery can complete without release/deployment readiness.
